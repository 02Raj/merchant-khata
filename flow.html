Merchant Desk — MVP system architecture

Mobile-first wholesale + retail ledger for Indian kirana and mandi merchants. React Native (Expo) talks to Supabase directly in MVP. Spring Boot is a later insertion point — the mobile contract is designed so screens do not need a rewrite.

Row Level Security

Every SELECT / INSERT / UPDATE / DELETE on tenant tables is gated by: JWT uid ∈ business_users for that business_id. Client-supplied business_id is never sufficient on its own.

Firebase — out of band

FCM for push (payment reminders, low stock) and Crashlytics for crash reports. No merchant ledger data is stored here. Tokens are registered against the signed-in user after Auth succeeds.

Later · Spring Boot API

Insert between Expo and Postgres without changing screens: same resources (sales, ledger, inventory), server-side authorization instead of (or in addition to) RLS. Mobile keeps a thin repository layer so the transport can switch from supabase-js to HTTP.

03 · Request lifecycle (happy path)

01 OTP login

Phone → Supabase Auth. JWT issued. Local session stored by Expo SecureStore.

02 Resolve tenant

Read business_users for uid. If none → Business Setup. Else pick active business_id.

03 Authorize

RLS policies join JWT uid to membership. Wrong tenant → zero rows, not an error toast.

04 Mutate

Sale / purchase writes parent + line items + inventory + ledger in one transaction (RPC or batched SQL).

05 Read back

Dashboard, ledger, inventory query only rows visible under the same membership.

06 Notify

Optional FCM after write. Crashlytics is independent of the data path.

05 · Security invariants (non-negotiable)

Tenant-owned tables require business_id

products, customers, suppliers, sales, purchases, payments, ledger_transactions, inventory_transactions all carry business_id NOT NULL with an FK to businesses. Line items inherit tenancy through their parent document.

RLS enabled before production

RLS is on for every public table. Policies cover SELECT, INSERT, UPDATE, DELETE. A table with RLS off is a ship blocker — not a “we’ll add it later” item.

Service-role never ships in the app

The Expo binary contains only the anon/publishable key. Service-role stays in server secrets (Edge Functions today, Spring Boot later). If it appears in a repo, env file committed to git, or the APK — treat it as a credential leak.

Do not trust client business_id

The app may send business_id for UX (which shop is selected). Postgres (and later Spring Boot) must re-check that auth.uid() is a member of that business. Authorization is membership, not a field on the request.

UNTRUSTED — anything from the device: selected business_id, role claims, prices, stock deltas.
TRUSTED — JWT subject from Auth, RLS policy evaluation, server-side RPCs / future Spring Boot checks.
